# Gazebo Humble Workspace — Self-Balancing Wheeled Biped Simulation

Welcome to the **Gazebo Humble** ROS 2 workspace! This project provides a full physics simulation of a self-balancing, two-wheeled bipedal robot equipped with 5-bar parallel leg linkages.

The control stack in this simulation is a line-for-line port of the real STM32 hardware firmware (from `RC_mcu_IK_wireless`), allowing PID gains tuned in simulation to transfer directly to the physical robot.

---

## 🔰 ROS 2 Crash Course for Beginners

If you are new to ROS (Robot Operating System), here are the core concepts used in this repository:

* **Workspace (`Gazebo Humble`)**: The top-level folder containing source code (`src`), build artifacts (`build`), compiled binaries (`install`), and execution logs (`log`).
* **Package (`gazebo_prep`)**: A self-contained folder under `src/` containing code, configuration files, launch scripts, and robot models.
* **Node**: A ROS process that performs computation (e.g., balance control, leg posture control, communication bridges).
* **Topic**: A data channel where nodes publish or subscribe to messages (e.g., sensor data on `/imu`, movement commands on `/cmd_vel`).
* **Service**: A synchronous request/reply mechanism used to trigger actions or switch modes (e.g., `/motors_enabled` to arm/disarm the robot).
* **Parameter**: Configuration settings that can be read or updated live at runtime (e.g., PID gains like `kp`, `ki`, `kd`).
* **Launch File**: A script (Python) that starts multiple nodes, bridges, and Gazebo simulation with custom arguments in one command.
* **URDF / Xacro**: XML format used to describe the robot's physical structure (links, mass, inertia, joints, 3D visual/collision meshes).
* **Colcon**: The ROS 2 build tool used to compile packages in a workspace.

## 📑 What File Does What (File-by-File Breakdown)

Inside `src/gazebo_prep/`, every file serves a specific role in bringing the robot to life:

### 1. Launch Files (`launch/`)
* **`launch/simulation.launch.py`**: The main entry point script for the simulation. It starts Gazebo Harmonic, loads the SDF world, processes the URDF robot model, spawns the robot lying down on its back, brings up `ros2_control` hardware controllers, launches the Gazebo-ROS parameter bridge (`/clock` and `/imu`), and starts all control nodes (`balance_point`, `standing_mode`, `rc_teleop`, `wireless_gui_bridge`).

### 2. Control Nodes (`src/` & `gazebo_prep/`)
* **`src/balance_point.cpp`**: The primary C++ controller node. Ported directly from the STM32 firmware (`main.cpp`), it runs at 100 Hz and implements a 3-layer cascade controller:
  * **Outer Layer**: Position hold $\rightarrow$ target velocity.
  * **Middle Layer**: Velocity PI $\rightarrow$ tilt bias (degrees).
  * **Inner Layer**: Balance PID $\rightarrow$ wheel effort/torque output.
  Handles raw accelerometer/gyro complementary filtering, IMU calibration, safety cutoff latches, motor torque limits, and high-frequency telemetry.
* **`gazebo_prep/standing_mode.py`**: Python node for leg posture management. Controls the two 5-bar linkage driver joints (`left_hip_rear`, `right_hip_rear`). When motors are armed, it smoothly moves the legs from the fallen angle (`-0.30` rad) to the stance angle (`-0.60` rad) using a smooth cosine velocity profile so the robot can stand up.
* **`gazebo_prep/rc_teleop.py`**: Python teleoperation mapping node. Converts standard `/cmd_vel` geometry messages into velocity targets and PWM turn bias. Reproduces physical FlySky RC transmitter behavior (stick deadband, acceleration limits, slew rate limiting).
* **`gazebo_prep/wireless_gui_bridge.py`**: Python TCP socket server running on port `3333`. Emulates the physical STM32 firmware's ASCII serial protocol over TCP (`P<val>|`, `I<val>|`, `M|`, `R|`, `C|`), allowing the physical robot's wireless GUI tuning software or `netcat` to tune parameters live in simulation.
* **`gazebo_prep/__init__.py`**: Python package initialization file.

### 3. Command Line Executable Wrappers (`scripts/`)
* **`scripts/standing_mode`**: Shell wrapper enabling `ros2 run gazebo_prep standing_mode`.
* **`scripts/rc_teleop`**: Shell wrapper enabling `ros2 run gazebo_prep rc_teleop`.
* **`scripts/wireless_gui_bridge`**: Shell wrapper enabling `ros2 run gazebo_prep wireless_gui_bridge`.

### 4. Configuration Files (`config/`)
* **`config/balance_params.yaml`**: Contains default runtime parameters for all nodes (PID gains `kp: 95.0`, `ki: 670.0`, `kd: 2.0`, complementary filter `alpha: 0.96`, encoder `counts_per_rev: 1320.0`, motor stall torque `0.15` N·m, stance angles, deadbands, safety limits).
* **`config/ros2_controllers.yaml`**: Hardware controller manager configuration for `ros2_control` (defines `joint_state_broadcaster`, `hip_position_controller`, `wheel_effort_controller`, and `wheel_velocity_controller`).

### 5. Robot Description Files (`urdf/`)
* **`urdf/assembly.urdf.xacro`**: Master robot kinematic and dynamic description. Defines links, masses, centers of mass, inertia tensors (derived verbatim from Fusion CAD), joint origins, limits, and 5-bar linkage `<mimic>` joints.
* **`urdf/assembly_ros2_control.xacro`**: Hardware interface definitions for `ros2_control` (position interfaces for driver hips, effort/velocity interfaces for wheels, state interfaces for mimic joints).
* **`urdf/assembly_gazebo.xacro`**: Gazebo-specific extensions (`ign_ros2_control` plugin, `MPU6050` IMU sensor configuration with realistic noise, surface contact friction/stiffness properties, optional SDF 5-bar foot closure joints).

### 6. Simulation World (`worlds/`)
* **`worlds/balance_arena.sdf`**: Gazebo Harmonic world file configured with a flat physics ground plane, lighting, 1 ms physics step size, and required Gazebo systems (`gz-sim-physics-system`, `gz-sim-user-commands-system`, `gz-sim-scene-broadcaster-system`, `gz-sim-imu-system`).

### 7. CAD Mesh Assets (`meshes/`)
* Contains 3D STL mesh models exported from CAD used for visual rendering and collision detection:
  * `pelvis.stl`, `left_femur_front.stl`, `left_femur_rear.stl`, `left_shank_front.stl`, `left_shank_rear.stl`, `right_femur_front.stl`, `right_femur_rear.stl`, `right_shank_front.stl`, `right_shank_rear.stl`.

### 8. Build & Metadata Files
* **`CMakeLists.txt`**: C++ build instructions for `balance_point` executable, Python package installation setup, resource file installation paths, and linter settings.
* **`package.xml`**: Package manifest specifying package metadata, maintainer details, build tool dependencies (`ament_cmake`), ROS dependencies (`rclcpp`, `sensor_msgs`, `geometry_msgs`, `std_srvs`), and controller packages.
* **`README.md`**: Package-specific documentation in `src/gazebo_prep/`.

## 🚀 All the Ways to Run All the Files

### Step 1: Open Terminal, Build & Source Workspace

Before running any ROS 2 commands, open your terminal and set up your workspace:

```bash
# Navigate to the Gazebo Humble workspace directory
cd ~/Documents/biped/Bipedal-URDF/Gazebo\ Humble

# Source your ROS 2 distribution (Humble or Jazzy)
source /opt/ros/humble/setup.bash

# Build the package
colcon build --symlink-install --packages-select gazebo_prep

# Source the workspace environment (REQUIRED after build)
source install/setup.bash
```

---

### Step 2: Run the Complete Simulation (Launch File)

The standard way to start everything (Gazebo GUI, robot model, controllers, balance stack) is using `simulation.launch.py`:

```bash
# 1. Standard Run (Default: launches Gazebo GUI, robot lying down)
ros2 launch gazebo_prep simulation.launch.py
```

#### Launch Options & Custom Arguments:

```bash
# Run Headless (no Gazebo graphical GUI window, uses less CPU/GPU)
ros2 launch gazebo_prep simulation.launch.py gui:=false

# Start partially reclined instead of fully flat (-0.8 rad instead of -1.35 rad)
ros2 launch gazebo_prep simulation.launch.py spawn_pitch:=-0.8

# Start at custom spawn height or coordinates
ros2 launch gazebo_prep simulation.launch.py spawn_z:=0.20 spawn_x:=1.0

# Experimental: Enable 5-bar SDF physical closure joints (for research)
ros2 launch gazebo_prep simulation.launch.py use_closure_joints:=true
```

---

### Step 3: Arming, Standing Up & Driving the Robot

Once the simulation is running, the robot spawns lying on its back. To interact with it:

```bash
# 1. Arm Motors (Triggers stand-up trajectory & enables PID balance loop)
ros2 service call /motors_enabled std_srvs/srv/SetBool "{data: true}"

# 2. Disarm Motors (Disables balance loop & resets integrators)
ros2 service call /motors_enabled std_srvs/srv/SetBool "{data: false}"

# 3. Drive Forward (publish velocity command of 0.1 m/s forward, 0.3 rad/s turn)
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.1}, angular: {z: 0.3}}"

# 4. Stop Driving
ros2 topic pub -1 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.0}, angular: {z: 0.0}}"

# 5. Re-trigger Standing Trajectory (without disarming/arming cycle)
ros2 service call /standing_mode/set_stance std_srvs/srv/Trigger
```

---

### Step 4: Live PID Gain Tuning & Calibration

You can adjust balance PID gains live while the simulation is running without restarting:

#### Method A: Via ROS 2 Parameter CLI
```bash
# Set inner balance Kp gain
ros2 param set /balance_point kp 110.0

# Set inner balance Ki gain
ros2 param set /balance_point ki 600.0

# Set inner balance Kd gain
ros2 param set /balance_point kd 3.0

# FLUSH INTEGRATORS after changing gains (Essential for clean A/B gain testing!)
ros2 service call /reset_state std_srvs/srv/Trigger

# Zero the pitch offset calibration
ros2 service call /calibrate std_srvs/srv/Trigger
```

#### Method B: Via Wireless ASCII Protocol (Netcat / GUI)
Connect to the TCP bridge on port `3333` using `netcat`:

```bash
nc localhost 3333
```
Type ASCII commands directly into the prompt:
* `P110.0|` $\rightarrow$ set balance Kp to 110.0
* `I670.0|` $\rightarrow$ set balance Ki to 670.0
* `D2.0|` $\rightarrow$ set balance Kd to 2.0
* `VP0.02|` $\rightarrow$ set velocity loop Kp to 0.02
* `M|` $\rightarrow$ toggle motor arm/disarm
* `R|` $\rightarrow$ reset integrators
* `C|` $\rightarrow$ calibrate IMU zero angle

## ⚡ Important Notes & Troubleshooting

1. **Robot Fails to Stand Up from Fully Flat**:
   The physical JGA12V motors produce 0.15 N·m stall torque per wheel (0.30 N·m total). Gravity torque at full flat lean (~77°) exceeds this torque limit. If the stand-up fails, spawn the robot partially reclined:
   `ros2 launch gazebo_prep simulation.launch.py spawn_pitch:=-0.8`

2. **Always Call `/reset_state` After Gain Modifications**:
   If you change PID gains while the robot is running, residual integrator accumulation will cause sudden transients that look like PID instability. Call `/reset_state` to clear integrators.

3. **Sign Convention Verification**:
   When armed, the wheels must drive **under** the falling direction of the body. If the robot accelerates in the direction it falls, flip the effort sign:
   `ros2 param set /balance_point effort_sign 1.0`
